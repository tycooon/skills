# Review All Open Pull Requests

Find every open, non-draft pull request (GitHub) or merge request (GitLab) across the requested targets, then review each one and keep watching them. A scheduled scan with no model in it finds the PRs that changed, and each one gets a fresh headless review run of its own (see *Running the watch*).

A target is a single repository, a whole group/org, a single PR, or several of any of these. The ask often mixes them, and often attaches a filter to some of them ("this group, all of it; that repo, only the PRs touching X; and this one PR"). One repository is just the one-target case; when the ask names no target at all, the target is the current repository.

Review the code, not the pipeline — the same scope review-pr sets, and it binds every review run. Don't pull up any PR's check or pipeline status, and never turn a failing, pending, or missing check into a finding, into a reason to withhold approval, or into anything you report. CI is the address-pr skill's business, not the reviewer's.

## Working out the targets

Resolve every target to a concrete list of projects before reviewing anything, and say what that came to in a line — the repos and how many open PRs each has, how many threads of yours from earlier runs the first pass adopted, plus the calls you found genuinely borderline, when there are any. Scoping is the user's to correct, and it is cheapest to correct on pass one, before a filter you guessed wrong has cost a dozen reviews or hidden a repo they cared about. That is the whole reason it gets said at all, so it is a line, not a write-up: no reasoning through each filter, no per-repo justification.

- **Group listings can include projects that aren't the group's own.** Shared projects show up alongside them. Decide deliberately whether "everything in group X" means X's namespace or the shared ones too, and name the choice in that line.
- **A filter like "only PRs related to X" is a judgment call, not a grep.** Judge by what the PR changes and why. A PR that merely *reads* a table another service owns is not "related to" that service — by that standard half the repo qualifies. A PR driven by that service's ticket, changing the contract between them, or syncing its tables, is. Apply the same bar to every candidate rather than letting a keyword hit decide, and name the borderline ones in that line; expect to be told you drew one of them wrong.
- **A PR named outright is a target of its own, and brings only itself.** It comes as a URL, `repo#N` or `repo!N`, or a bare number in the current repository, and the scan reads that one PR rather than listing its repository. Naming it is an explicit ask: it is reviewed even as a draft or past the dormancy cutoff, and a filter on its repository doesn't drop it. Its credential and clone are its repository's, as for any target. When it merges or closes it has finished, not failed — the tick takes it out of the watch and logs it; a review of it still in flight falls under review-pr's *When the PR merged before the review was ready*.
- **Credentials are per target.** A group-scoped bot token returns 404 on every project outside its group. Test each target's posting credential once, up front — a project fetch with the token exported, per review-pr's *Posting identity* section — rather than discovering the gap when a run's first post fails. Two traps there, both of which have bitten: never write a shell test for whether the token variable is set (the near-miss forms print the token itself), and never read a 200 as proof the token exists, because `gh` and `glab` fall back to their config account when the variable is empty. Confirm the identity — `glab api user | jq -r .username` with the token exported — then confirm that identity's reach on each target. Judge it by the name: a bare `null` there means the token is set but dead, and the pipe through `jq` hides that behind a zero exit. Where no credential covers a target, post with the default account and keep the identity line; attribution lives in the comment body, not in the avatar. Name those targets in the scoping line whenever the default account also authors PRs there. GitHub refuses self-approval, so a clean review of such a PR can only end in an APPROVED comment, not the formal approval review-pr asks for. Giving the bot access to the target is what makes a formal approval possible, and that is the user's call, not yours.
- **Prefer local clones.** Reviewing from a clone beats API-only reads by a wide margin — the run can grep the whole tree, follow callers, and read files the diff never touched. Each run fetches the clone of its PR's repository itself, then works strictly read-only against explicit shas (never check out a branch, never create a worktree, never modify the clone). Runs share clones, so a fetch that fails on a lock is retried, not treated as a dead repository. Where no clone exists, the run reviews through the API.
- **Runs inherit the scheduler's environment.** The scheduled tick runs under a login shell, so the posting tokens your profile exports reach every run. A token you exported only in this session does not. Check that the profile provides it before `install`.

## Running the watch

A watch is not a long-running agent session. `~/.claude/bin/review-scan` (installed by the skills repo's `bin/setup`) scans the targets on a schedule without any model, and starts a fresh headless `claude -p` run for each PR that changed since a run last settled it. A quiet PR costs one line of a listing and nothing else, and no session carries hours of context from tick to tick. `review-scan --help` and the script's docstring cover every option.

**Setting one up** is the part you do in this session, once:

1. Work out the targets and test their credentials as *Working out the targets* says, and give the scoping line.
2. `review-scan init <watch> --target SPEC… --own LOGIN… [--filter SPEC=TEXT]… [--token SPEC=ENV_VAR]… [--reviewer-model MODEL] [--effort LEVEL]`. `--token` names the variable holding a target's posting token when the default reviewer-bot variable can't post there, such as a second GitLab host with its own bot; that target's runs post with it, and its bot belongs in `--own` too. `<watch>` is a short name of your choosing. A filter is the user's words, which the run applies as the judgment call that section describes. `--own` is required and lists every account that posts as you on these targets: the reviewer bot and your default account both. An account left out reads as someone else, so every settle of a PR it posted on is refused and the PR is reviewed again on every tick. The reviewer model is `opus` unless the user names another; pass whatever they ask for, and `--effort` the same way (default `medium`).
3. `review-scan tick <watch> --full --dry-run`, then read its accounting lines: one per target, listed and kept counts, drafts, dormant PRs, and `UNREAD` for a target that could not be read. Fix any unread target before going on. Then run the first pass for real with `review-scan tick <watch> --full`: the first pass checks every open PR in full, since the delta can only see what moved after the state began.
4. `review-scan install <watch> [--interval SECONDS]` (default 120) schedules the tick: a launchd agent on a Mac, a crontab line elsewhere. Then tell the user the watch name, the reviewer model and how to stop it.

**What the tick does.** It lists each target once and skips drafts (unless named) and PRs with no activity for `--dormant-days` (default 14). Then it starts a run for each PR whose head or last activity differs from what the last settled run recorded, each PR never settled, and each a sibling or a nudge marked for a recheck. At most `--max-parallel` runs (default 3) go at once, never two for one PR, and the rest wait for a later tick. A run that ends after a minute or more starts a tick itself, so a freed slot is refilled at once rather than at the next scheduled tick; a run that ends sooner starts none, so one that dies on start can't spin the watch. Such a tick does nothing once the watch is uninstalled, so `uninstall` stops the chain as well as the schedule. A PR named by URL leaves the watch once it merges or closes, and a watch with nothing left in it says so. One target failing doesn't stop the others: the tick reports it and exits 5.

**What settles a PR.** A run ends with `review-scan settle`, which records the head it reviewed, the verdict, the PR's activity time and the threads it weighed and left silent. The command refuses (exit 3) if the head moved during the run, and refuses (exit 4) if anyone not in `--own` posted after the run started. Then the next tick sees the PR as changed and starts a fresh run, so a reply that landed mid-review is never lost. It also refuses (exit 6) when the PR doesn't show the verdict the run claims: `approved` needs an approval of ours at the head, an APPROVED post of ours from this run where a formal approval is impossible, or, with `--covered-by <sha>`, a formal approval of ours at that earlier head (an APPROVED post naming it only where a formal approval is impossible), and `findings` needs an open thread of ours. The check is a gate against a run forgetting the verdict, not a judge of it: whether an earlier approval still covers the head under review-pr's *Only a formal approval covers a head* is the run's call, and settle takes its word. That gate is what keeps *A verdict you have not given* from going silent: a settled PR is quiet until it moves, so it may only settle once the verdict is on it. A recheck stays on the PR until a settle succeeds, so a run that dies doesn't lose it. A run that dies before settling leaves the PR owed. Its replacement's brief says when the dead run started, so it checks what already landed before posting.

**When a watch has trouble.** The tick sends a desktop notification once when a new problem starts (on a Mac; elsewhere it writes the problem to `cron.log` in the watch's state directory, the file the printed crontab line appends to), and `status` shows it on its first line until it clears. Three problems qualify:

- none of the targets could be read, usually an expired token or lost access;
- a review run failed to start, such as `claude` missing from the login shell's PATH, or its CLI logged out (its login is separate from the desktop app's; `claude auth login` restores it);
- nothing is left to watch, because every named PR merged or closed.

Transient trouble with one target is not a problem of the watch: the tick reports it as `UNREAD` and tries again next time.

**A watch never stops on its own.** There is no quiet cap and no error stop. A quiet watch costs a listing per tick and no model. A broken one notifies and keeps trying, so it recovers by itself once access returns. Only `uninstall` stops it.

**Status, nudges and stopping.**

- `review-scan list` (or `status` with no name) shows every watch on the machine: its targets, reviewer, whether it is scheduled, runs in flight and any problem. A nudge needs no watch name.
- `review-scan status <watch>` shows the config and the last tick, then the PRs in four groups: runs going now (when each started, why, and its log), PRs waiting for a free slot, runs that ended without settling on PRs still open, and settled PRs with their verdict and head.
- `review-scan nudge <pr-url> --head <sha>` makes every watch covering that PR look at it at once; address-pr's push step sends it. A nudge never changes the schedule.
- `review-scan account <watch> <config dir>` moves the watch's runs to another Claude account: a config directory with its own login (`CLAUDE_CONFIG_DIR=<dir> claude auth login`), which the command links your rules, settings, skills and plugins into, so reviews behave the same. `review-scan account <watch> default` moves them back to the CLI's own login. Runs already going finish on the account they started with.
- `review-scan model <watch> <model> [--effort LEVEL]` changes the model or effort of the watch's runs in place, keeping its targets and state; runs already going keep theirs.
- `review-scan uninstall <watch>` stops the schedule and kills runs still in flight. The state stays on disk, so `install` later picks up where the watch left off. After a long gap, start with a `tick --full`.

Each run's brief, its stream-json log and its pidfile sit in the watch's state directory under `runs/`. When the user asks how a review went, read the log there; don't rerun the review.

## What a PR still owes you

Before picking up a PR, work out what it still owes you, from four independent checks. **New code:** compare the current head against the commit you last reviewed with the base-sync test in review-pr's *Re-reviewing a PR you have already reviewed* — any change to the PR's authored lines counts, and a sync that leaves them identical does not. **Threads waiting on you:** go thread by thread and find the open ones whose *last comment is not yours* and that you have not already weighed at the current head. **A sibling moved under it:** a PR whose own head and threads are untouched can still have been invalidated by another PR in the sweep — see *When a sibling moves under a quiet PR* below. **A verdict you have not given:** a PR with no open threads and no approval of yours covering the current head, as review-pr's *Only a formal approval covers a head* defines it — one naming it, or an earlier head it differs from only by a base-sync — is not a settled PR — it is one waiting on you, and nothing about it will ever say so. Skip the PR only when all four come back empty. Always review PRs you have never reviewed — unless they are dormant, which is settled first and on its own.

Decide the thread question by last commenter, never by a timestamp. Comparing "the most recent review I left" against "the most recent reply on the PR" collapses per-thread state into two numbers, and then any thread whose reply is older than your latest action *anywhere on the PR* hides behind it: answer one thread, and every older thread reads as caught up — permanently, because your own timestamp only moves forward. The same goes for asking which replies arrived since the last round, which silently drops anything that landed while you were busy elsewhere in that round. Last-commenter has no such blind spot: a thread you haven't weighed keeps failing the test every round until you do. On GitHub that is one `reviewThreads` query and a look at `comments.nodes[-1].author`; on GitLab, the last note on each unresolved discussion.

**Drop the platform's own notes before asking who spoke last.** GitLab writes system notes *into* review threads: «changed this line in version N of the diff» arrives as a note on the thread, attributed to whoever pushed. So a thread the author has never answered reads as though they replied, and the pass goes hunting for pushback nobody wrote — then either posts a redundant answer or, worse, treats the finding as contested. Discard notes the API flags as system-generated (`system: true` on GitLab; timeline events rather than comments on GitHub) and judge by the newest human-written note. A thread whose only new notes are the platform's is untouched, which puts it in the silent case.

Weighing a thread usually ends in posting nothing — review-pr leaves an unfixed finding's thread open and silent rather than nagging it on every push — and such a thread keeps the author's reply as its last comment, so on last-commenter alone it would read as waiting on you every round forever. So: once you have weighed a thread at a given head and chosen to stay silent, it is settled for you until something new lands on it — a new push, or a new reply. Carry that with the rest of your per-PR state. Losing it costs one extra look and nothing else, since the silent outcome posts nothing either time.

**That record is the only thing you may carry about a thread — never the thread question's answer itself.** A note reading "1 open thread, waiting on the author" is a cache of a remote state the author can change a minute after you wrote it, and a tick that reads its own note instead of the threads is answering from memory. The failure is silent and it does not heal: a stale "waiting on them" reads exactly like "nothing owed", so the PR comes back clean on every tick that follows and nothing in the output ever contradicts it. Contrast the direction each one fails in. The "weighed at this head" record going stale costs one redundant look at a thread that had nothing new on it, and anything that does land unsettles it again — it can only ever hand you *more* work than you need. A stale thread count hands you less, and what it takes away is the PR. So re-read the threads themselves every time you evaluate a PR; that is one API call, not a review.

**Reopening a thread — or any reply of yours on one — starts a wait, not the end of one.** Posting on a thread is an invitation to answer it, and an author who is actively working answers in minutes rather than days. The settle after your post records the PR's activity time with your post in it, so the author's answer moves that time and the next tick starts a run to read it.

A PR can need you again with no new commit at all. Instead of pushing code, the author often pushes back on a finding in its thread, explaining why they did not make the change — exactly what the address-pr skill does when it judges a comment wrong. Or the fix is simply not code: a finding about a misleading PR description is addressed by editing the description, and a branch that never gets pushed keeps the head sha it had all along. Head-sha movement is not a proxy for "something happened here" — going by commits alone leaves both the pushback and the fix unanswered forever.

**A verdict is owed work too.** A PR with no open threads and no approval of yours covering the current head, as review-pr's *Only a formal approval covers a head* defines it, is not finished, it is waiting on you, and it is the one owed state in this section that produces no signal whatsoever: no new head for the delta to catch, no unanswered thread for the last-commenter test to fail on, nothing at all for the cheap scan to notice. It is also the state every successful round ends in, one beat before the approval, which makes it the easiest one to leave a PR sitting in — and a PR left there looks finished to everyone except you. So check it explicitly rather than waiting for it to announce itself: zero open threads and no covering approval under that rule means pick the PR up, review whatever you have not, and post the verdict — the approval, or the finding that stops you giving one.

### PRs nobody has touched in weeks

A sweep is for work in flight. The tick skips any PR whose last activity is older than the watch's dormancy cutoff, two weeks by default, including one never reviewed, and counts it in that target's accounting line. Left in, abandoned PRs are the expensive ones: a branch months behind its base has an enormous diff and yields findings nobody is waiting for. Your own comments count as activity, so a PR you are mid-conversation on stays in, and any push or reply brings a dormant PR back with no bookkeeping. Name the cutoff when you report skips, so the user can set a different one with `init --dormant-days`. A PR the user names outright is reviewed whatever its age.

Be honest about the trade. A long-dormant PR is not automatically harmless — one abandoned for months can carry an early draft of work that has since landed by another route, so merging it would revert the better version. This rule accepts that risk deliberately: it belongs to whoever merges the PR, not to a sweep that would otherwise never converge.

### When a sibling moves under a quiet PR

A change often spans several open PRs — a producer and the doc describing its contract, a base PR and the one stacked on it. When one of them lands a fix, the others can become wrong without anything happening to them: rename an error code and the PR documenting that code is now stale; change a signature and the PR on top of it no longer compiles. Both checks above stay silent — head unchanged, no new replies — so the staleness is invisible to exactly the signals you rely on, and the quiet PR sails through pass after pass being wrong.

So when a run changes the picture for a PR that another open PR documents, consumes or builds on, settle with `--recheck <sibling url>`: that sibling then owes a look regardless of its own activity, and its next run's brief carries the reason. Say on your own PR's thread or in your review what moved and where, so the sibling's run can find it, and expect the re-review to cut both ways: some of its standing findings will be obsolete and need withdrawing, per *Picking a PR back up*, while the change itself may have introduced new ones.

### Knowing which head you last reviewed

The record — PR → the head you actually reviewed, and the threads you weighed and left silent at it — is review-scan's state, written by `settle` at the end of every run, whether or not the run posted anything. It reaches the next run in its brief. Never try to rebuild it from what's visible on the PR instead; every such reconstruction has a failure mode:

- **Comment anchors are not a record of what you reviewed.** GitLab re-anchors an inline note's `position.head_sha` to the newest diff version whenever the line still maps. So a PR that was pushed to five minutes ago reads as already reviewed *at the new head* — and the run skips real new code, silently, with nothing in the output to suggest anything was missed.
- **A run that posts nothing leaves no trace.** "Reviewed, nothing to say" is a common and correct outcome — a base sync, an untouched thread — but it creates no note, so an inferred head never advances.
- **A reply inherits its thread's original anchor**, so answering a thread at a new head doesn't mark that head either.
- **An APPROVED note naming a sha is reliable** — it's immutable text you wrote — **but only when it is your newest note.** An older approval must never override findings you posted later at a later head.
- **A PR you requested changes on carries no anchor at all**, because a pass with findings posts no verdict note — only threads, whose positions GitLab re-anchors. So for exactly the PRs you are most actively working, the record is the *only* trace of what you read.

When a brief carries no settled head — the first run of a watch, or state lost — the least-bad source is the PR's diff-version history: take the version that was current at the time of your newest comment, remembering that a **retarget** writes a fresh diff version carrying the *same* head, so a new version is not by itself evidence of a push. Then correct it against the PR itself; the settle that ends the run records the result.

When the checks disagree, re-review. A false "already reviewed" silently drops real code; a false "changed" costs one run that finds nothing new. Those are not close in cost.

**Consult that record *after* the threads-waiting-on-you check, never before.** The record's whole job is to stop a head you deliberately said nothing about from reporting as new work forever — but the same head can perfectly well owe a reply, because the author answered a thread without pushing. Order the checks so the record can only ever settle the *new code* question: threads first, record second. Getting that backwards turns your own bookkeeping into a way to lose replies, which is worse than the re-flagging it was there to prevent.

### Telling your own comments from everyone else's

review-pr's *Whose comment it is* decides this — an account you post from and your identity line, both at once — and it is also what makes threads from earlier runs yours to pick up. Two things about it are particular to a sweep.

Across several repos your reviews will not all sit on one account: a dedicated bot where one is configured, your default account where that bot has no access, and older reviews from before the bot existed. Work out per target which accounts are yours, and have the scan test both conditions on every comment. A scan that goes by the account alone disowns every earlier review posted from your default account, whose threads then never get resolved and hold your verdict back for good; one that goes by the body alone claims a teammate's AI review that carries your banner.

A PR's first run in a watch adopts every thread of yours already on it, whichever session posted it, so a new watch picks up where the earlier ones stopped instead of treating their threads as someone else's.

Decide ownership on every scan, from those two conditions applied to the thread itself. Never carry a skip-list of thread ids or signatures from one pass to the next: a thread filtered out once as someone else's is never weighed again, so when the PR's author fixes the finding, the fixed thread stays open and holds back the approval, and no later scan reports it. A signature you cannot place is a reason to read the thread, not to drop it.

### Picking a PR back up

When you do pick a PR back up, handle it exactly as review-pr's *Re-reviewing a PR you have already reviewed* section says — that section is the single source for what to post and what to leave alone: review whatever code is new, resolve the threads that are now settled (resolving is the reviewer's job, not the author's), reply only on the threads that genuinely need it, and approve once nothing is left standing. Two of its rules matter most on a sweep like this, where the same PRs come back round after round: don't comment on an open thread just because a push happened, and don't re-post a finding that already has a thread.

Findings of yours that turn out to be wrong are withdrawn, not left standing. That includes the ones no one argued against: if a later pass — or a sibling PR's review — turns up evidence that a finding was mistaken, say so on its thread, explain what changed your mind, and resolve it. An open thread asserts a defect on every future pass, so leaving a known-wrong one open is worse than never having posted it.

## One run reviews one PR

This is the section a review run follows: a headless `claude -p` session that review-scan started with a brief naming one PR. Nobody reads its chat output, so the PR is the whole report, and the run ends with `settle` or with nothing.

1. **Read the brief as starting points, not premises.** It is written from a scan, so its factual assertions age while the run works and some were shaky when written: which shas moved, whether anyone has replied, what a sibling PR is for. Read the PR's threads from the API yourself and judge against the live head. When the brief and the code disagree, trust the code, act on it, and say so in the review where it matters.
2. **Note the head you are reviewing** before you read the diff, and review at that sha. If the PR's target carries a filter, decide first whether the PR falls inside it; a PR outside it is settled without a review.
3. **Work out what the PR owes you** with the four checks in *What a PR still owes you*, using the brief's last settled head and weighed threads. An earlier run that never settled is named in the brief: before posting, query the PR for anything of yours newer than that run's start, and post only what is not already there.
4. **Review and post** as review-pr says, from its *Posting identity* through its verdict rules and *Re-reviewing a PR you have already reviewed*. Post each finding as an inline review comment anchored to its file and line — submitted as one review, with nothing summarizing the findings alongside them — never as a single top-level PR comment, which the "address comments" auto-fix and the address-pr skill cannot detect, and **never as a changes-requested verdict note**. Prefix each finding with its severity (P0–P3). A pass with any P0 or P1 posts the threads and nothing else. A pass whose findings are all P2/P3 approves the head, with those findings as the approval's inline comments marked non-blocking. An RFC PR — its title tagged `[RFC]` — also gets review-pr's *RFC pull requests* treatment: one thread per open question, and no approval while one is open or waiting on the owner. A review with no findings approves the PR as review-pr's clean-review rule says, including its exception for a host whose instructions forbid a formal approval. Every comment includes your identity (AI agent name) — the approval verdict included, since that identity is the only thing that lets a babysit-pr watch tell a review verdict from a teammate's Approve. Post under the reviewer-bot account when one is configured for that target, exporting `PR_REVIEW_GH_TOKEN` (GitHub) or `PR_REVIEW_GITLAB_TOKEN` (GitLab) for just the posting commands when the variable is set. When the brief names another variable for this target, export its value under that default name instead, so every posting command and helper script reads it. Read review-pr's *Posting mechanics* before the first post, not after one fails.
5. **Check related PRs against each other.** The brief lists the watch's other open PRs. When one change spans a contract, a producer and a consumer, read the halves against each other instead of against the prose. A defect that lives purely in another PR's code belongs to that PR's run: settle with `--recheck` on it rather than filing it here.
6. **Write only inside your own scratch directory.** Several runs share the machine and the clones, so use a per-PR subdirectory for every file you write, and never write to a clone.
7. **Settle** with the command the brief ends with: the head you reviewed, the run start time from the brief, the verdict you left (`--verdict approved`, `findings`, or `outside-filter` for a PR the target's filter excludes; with an earlier approval that still covers the head, `--verdict approved --covered-by <that head>` rather than a second approval), each thread you weighed and left silent (`--weighed`), and each sibling whose picture you changed (`--recheck`). On exit 6 the verdict isn't on the PR yet: post it, or work out why your post did not land, then settle again. On exit 3 or 4, stop: the head moved or someone posted while you worked, and the next tick starts a fresh run with the new state. Never retry the settle with a different head to make it pass.

## Report

**The PR is the report.** Findings live on the PR, in context, where they can be answered and resolved; a copy in chat is a second version of the same text that goes stale the moment a thread moves, and nobody acts on it there. So what you write to the user is pointers and counts — never a finding, never what a review concluded, never a PR-by-PR account of a sweep the user can open and read.

Setting a watch up ends with one short message: the scoping line, the watch name, the reviewer model, the first pass's counts (PRs reviewed, skipped as draft or dormant with the cutoff, targets unread), and how to stop it. After that the watch reports nothing on its own beyond the notifications above. When the user asks how it is going, read `review-scan status` and answer with counts and links to the PRs left carrying standing findings. When it is stopped, give the same short summary, grouped by target when there is more than one.

Whenever you name a PR/MR in anything the user reads, give it as a clickable markdown link to the PR/MR's full URL (e.g. `[!170](https://gitlab.domain.com/group/repo/-/merge_requests/170)`), never a bare number or title.
