# Release

Carry one PR/MR through readiness, merge, deployment and release verification. For example, `/release 42` waits while PR #42 has an unresolved discussion, then merges and deploys it once all four babysit-pr conditions pass.

## Bind the request

Resolve the number/URL supplied by the user, or the PR/MR for the current branch. Pin its host, repository/project, number and base branch; never switch targets on a later wake-up. Ask only if the target is ambiguous. An explicit `/release` invocation authorizes merging and deploying this target when ready, including scoped address-pr fixes during the wait. Automatic skill selection alone does not authorize either action; obtain missing authorization before enabling delivery. Preserve any narrower environment or release limits the user gave.

Read the project's merge and deployment instructions, identify its deployment command or automatic release workflow and destination, and record them with the request. Also identify a local install: a project whose checkout is used on this machine (a skills or dotfiles repo synced by its setup script, a CLI or tool installed from the checkout) is installed from the merged commit with its own setup command. A project may have a deploy, a local install, both, or neither. Recover these from repository configuration and existing release procedures; ask if the project deploys but its destination or procedure cannot be determined. Do not invent a deploy command or broaden the release to unrelated work. A stacked PR targeting another feature branch must reach the intended release branch through address-pr before delivery; merging into a feature branch is not a production release.

## Reuse the watch

Use [babysit-pr](../babysit-pr/SKILL.md) for readiness checks, address-pr rounds, cadence, quiet limits and scheduled recovery. Keep its approval definition, including the external AI reviewer's sign-off and the base-sync equivalence test; also satisfy the host's required approvals and merge rules. Do not supply your own approval or resolve discussions to pass the gate.

First find an active babysit-pr watch for this exact target in the current session's state and scheduler jobs. Adopt its state file and enable delivery there before the ready condition can end the watch. Keep its watch start, activity mark, quiet count, next due time, pending wake-up and backup heartbeat; do not reset or duplicate them. Existing wake-ups must read the delivery mode from the file. If a round is in flight, hand the mode change to its owner between rounds so only one owner acts.

If the watch belongs to another session, use the runtime's supported handoff to let that owner enable delivery and acknowledge it. Never infer ownership from a job name or alter another session's authorization blindly. If you cannot hand off safely, ask the user to invoke `/release` in the owning session; do not start a competing loop. An unrelated watch is not reusable and must not be replaced or canceled.

If no active watch exists, start one babysit-pr loop with delivery enabled, run its first round immediately, and arm its waiting transport (babysit-pr's *Waiting between rounds*). A stopped watch is not active; a new run gets a new watch-start floor. If scheduled resumption is unavailable, report the limitation instead of claiming to wait.

When Auto-fix is on for the PR in the Claude desktop app and `WatchPullRequest` is absent, the waiting transport is babysit-pr's *Background waiter*: Auto-fix's events drive the fix rounds, and `wait-pr-ready` brings the session back once the PR is ready, since Auto-fix sends nothing for green CI or an approval. Make sure a waiter is armed for the current head at the end of every round, as babysit-pr describes. Never tell the user you are waiting for CI or an approval unless a waiter, a native watch or a polling wake-up is armed for this target; without one, nothing resumes the release. A waiter exit 15 means the PR conflicts with its base, and 14 that findings landed: run the scoped address-pr pass now (for a PR Codex owns, resume Codex as the codex skill's step 4 does), then re-arm for the new head. A conflict the pass left in place goes to the user, and its head is recorded as `knownConflictHead` in the state file, so every later waiter armed for that head, after any wake or a waiter that died, carries `--known-conflict`. A release that waits on a PR Codex owns uses the codex skill's watch, which keeps that waiter armed until delivery.

Persist the target, authorization source and scope, deployment destination/procedure, local install command, `deliveryMode: merge-and-deploy`, `deliveryPhase: waiting`, and later the verified merge commit, deployment/run identifier, skipped-deploy reason, local install result and outcome in the watch's state file. The phases are `waiting`, `merging`, `deploying`, `installing`, `verifying`, and `complete`; errors or cancellation stop with the last confirmed outcome. Record each phase before its external action, so recovery reconciles host/release records before attempting anything again.

## Deliver when ready

Whenever a delivery step returns to waiting, re-arm the watch's transport for the current head before yielding: under Auto-fix nothing else resumes the release once the PR is ready again. A head this delivery just pushed gets a plain `--head <new head>` waiter.

1. **Recheck immediately before merging.** Read fresh host state for the current head: green CI, every discussion resolved, approval covering that head and all required approvals, no conflicts and no other host merge block. Pending, missing, failed or unknown checks are not green. A project with no CI at all (no pipeline or workflow configuration, and no checks reported on any recent head) skips the CI gate, including babysit-pr's pipeline condition while waiting; say so in the final report, and keep every other gate. A project that has CI but reports no checks for this head is still waiting, not exempt, until it is clear none will come: GitHub Actions starts a push's runs within seconds, so a head that still has no workflow run (`gh api "repos/<owner>/<repo>/actions/runs?head_sha=<head>"`) 10 minutes after it was pushed probably matched no workflow's path filters. The timeout alone does not prove it, because Actions sometimes creates runs late, so read the `paths` and `paths-ignore` filters of the workflows triggered by `push` or `pull_request` and confirm the changed files match none of them; only then does it skip the CI gate the same way. A `pull_request` filter sees the PR's whole diff. A `push` filter sees only what the push changed, so there compare the files changed since the last head whose runs passed: a README-only commit on top of a green head is covered by that head's runs. With no earlier head of this PR whose runs passed, as on its first push or on a fork, where base-repository `push` workflows never run, compare the PR's whole diff against the base; a head whose diff matches a filter is still waiting, not exempt, even when those runs can never come. A head whose files match a filter is still waiting. Say so in the final report too. Unknown mergeability is not permission to merge. Any authored change invalidates stale readiness; keep watching until all gates pass together again. Use the host's expected-head guard where supported, and its protected merge path without administrator bypass. If the head changes or the host rejects the gate, return to waiting and recheck; when the head is unchanged, the re-armed waiter gets `--after` set to the mark from the exit this recheck refused, so it waits for the PR to move. Do not force the merge.
2. **Check the merge result when the base has moved.** CI on the head proves that head only, not its merge with commits the base received since, and two PRs that each pass alone can break the base together. After a fresh fetch, if the base tip is not an ancestor of the head (`git merge-base --is-ancestor origin/<base> <head>`), build the would-be merge in a scratch detached worktree: `git merge-tree --write-tree origin/<base> <head>` gives its tree, `git commit-tree <tree> -p origin/<base> -p <head> -m check` a commit to check out. Run there the fast checks the project's instructions name for this gate, static checks that finish in seconds such as formatters and size or lint limits; never a build or test suite, which stays CI's job on the head. Remove the scratch worktree either way. A failure blocks the merge, and nothing else will act on it: the PR still meets babysit-pr's ready conditions, and a base that merely moved is not one of address-pr's base-merge cases. So run that fix here, as a scoped address-pr pass with the failing check's output: merge `origin/<base>` into the branch, fix what the check reports, rerun the check on the result, push, and return to waiting for CI and approval on the new head. Then right before step 3 merges, fetch again and confirm `origin/<base>` is still the tip the check used. If it moved, run this step again, because the host's expected-head guard pins the PR head, not the base. A project that names no fast checks skips this step; say so in the final report. The check catches static breakage only, not two changes that compile but fail tests together.
3. **Confirm the merge.** Use the project's merge method and verify the target is merged, which branch received it, and its merge commit. A closed, unmerged PR stops without deploying. If someone else merged it, confirm the authorized change landed on the intended release branch before proceeding. After a timeout or uncertain response, query the host before retrying.
4. **Deploy the confirmed change, if it needs one.** Skip the deploy, and its verification in step 6, when the merged diff changes nothing the deployed artifact runs: only docs, CI configuration, tests, or repository tooling outside the shipped artifact. Judge from the files the merge actually changed, record the reason, and name it in the final report. When any changed file could reach the running artifact (code, dependencies, build or runtime config, migrations, assets), or you are unsure, deploy. An automatic release run that starts anyway is not yours to cancel; observe it as usual. Otherwise, follow the project's procedure with its required environment loaded. For automatic deployment on merge, observe the existing release run rather than launching another. Verify the selected artifact/revision includes the merge commit. Other commits already on the release branch ship with it without asking; name them in the final report. Persist the run/release identifier and reconcile it on recovery. Do not repeat a successful deployment or blindly retry an uncertain production action; inspect the release record first. A failed deploy stops with the merge outcome and the concrete failure; rollback or additional remediation needs its own authorization unless already covered.
5. **Install locally, if the project has a local install** and the merged diff changes what it installs. Bring the checkout the install reads from to the merge commit, fast-forward only; if it has uncommitted changes or local commits, or is not on the release branch, stop and report rather than overwrite them. Run the project's setup command, then check that the installed copy matches the merged commit. When the installer leaves behind what the change removed or renamed, such as a renamed skill's old directory, remove those stale copies too and list them in the report.
6. **Verify and finish.** For a deploy, confirm rollout completion and the running revision, then use [check-after-deploy](../check-after-deploy/SKILL.md) for checks scoped to the change, compared with the pre-deploy baseline. Mark complete only after verification; report any unchecked behavior explicitly. Cancel this watch's wake-up and backup on completion, a hard error, cancellation or the inherited quiet cap. Use session-wide stop only when those jobs all belong to this watch; otherwise cancel only the owned jobs.

Stay quiet on unchanged rounds. Report meaningful fixes and once when merging/deploying begins. The final report names the PR/MR, merged commit, deployed revision/destination and verification result (or why the deploy was skipped), the local install result, or the exact point where delivery stopped and what remains. Never describe a merged PR as deployed without release evidence.
